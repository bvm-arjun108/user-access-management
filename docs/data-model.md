# Pharos UAM data model

One employee has one unique Okta account ID. Provisioning and updates carry the complete current Pharos role list for that employee.

## Tables and uniqueness

| Table | Stores | Primary key | Duplicate prevention |
| --- | --- | --- | --- |
| employee | Profile, Okta ID, manager, job details and supplier | employee_id | Unique nullable okta_account_id |
| ipass_role | Source role definition, flags and nullable env | role_id, generated UUID | Unique entitlement_value |
| employee_role_assignment | Current and historical employee-role assignments | assignment_id, generated UUID | One open assignment per employee_id + role_id |
| ipass_event | Submitted payload and latest processing result | event_id, UUID from iPass | One row per event UUID |

Four tables, 59 columns and four foreign keys. Employee and Okta IDs are source strings. Internal role and assignment UUIDs are generated by PostgreSQL.

## Relationships

~~~mermaid
erDiagram
    EMPLOYEE ||--o{ EMPLOYEE_ROLE_ASSIGNMENT : has
    IPASS_ROLE ||--o{ EMPLOYEE_ROLE_ASSIGNMENT : assigned_as
    IPASS_EVENT ||--o{ EMPLOYEE_ROLE_ASSIGNMENT : creates
    IPASS_EVENT o|--o{ EMPLOYEE_ROLE_ASSIGNMENT : closes
~~~

Each assignment references one employee, one role and its creation event. Its removal event is optional until closed. All four foreign keys use ON DELETE RESTRICT. Removing the last role does not delete the employee or shared role definitions.

An active employee must have an Okta ID. A minimal termination record may have no Okta ID; multiple NULL values are allowed by the unique constraint. An existing employee/Okta link cannot be changed by ingestion, and the same Okta ID cannot belong to another employee.

## Payload mapping

| Payload | Stored in employee, unless stated otherwise |
| --- | --- |
| user.employeeId | employee_id; source Owner ID |
| user.oktaAccountId | okta_account_id; unique employee attribute |
| user.sourceSystem | source_system: WORKDAY or VNDLY |
| user.employeeClass | employee_class; source classification such as Employee or Contractor |
| user.companyName | company_name |
| user.businessUnit / city | business_unit / city |
| user.manager | manager_employee_id, manager_first_name, manager_middle_name, manager_last_name |
| user.jobDetails | department, job_code, job_title, job_family_group, job_family |
| user.supplier | supplier; contractor supplier name |
| user.iPassRoles[].entitlementValue | ipass_role.entitlement_value |

ACTIVE snapshots require the fields shown in Swagger except email and supplier. Both may be omitted or null; either clears the saved value. Employee and manager middle names may be null. All five jobDetails keys are required, but their values may be null. ACTIVE requires terminationDate: null.

Manager IDs are source attributes; the manager does not need a Pharos employee record. Source Owner First/Last identify the employee. Role ownership is not supplied.

## History and reads

Role lists reconcile per employee. Omitted roles are closed; [] closes all current assignments. Shared role definitions and closed assignments remain. Reassignment creates a new assignment period. Termination closes current assignments; approved USER_PROVISIONED can restore access.

The internal GET returns `employee` (including okta_account_id) and `assignments`. Assignments are current by default; includeHistory=true also returns removed periods. No current roles means assignments: [].

## Processing and timestamps

| Column | Meaning |
| --- | --- |
| employee_last_synced_at | When iPass refreshed employee details from Workday/VNDLY |
| event_effective_at | When the reported change took effect |
| received_at / processed_at | Pharos first receipt / latest processing completion |
| assigned_at / removed_at | Source assignment start / when Pharos closed the assignment |
| assignment_event_id / removal_event_id | Event that created / closed the assignment |
| created_at / updated_at | Pharos record timestamps |

Event status is RECEIVED, APPLIED or FAILED. Business changes and APPLIED status commit together. Failures roll back business changes and record the failure where possible. Identical applied retries do not repeat changes; changed content under the same UUID returns HTTP 400.

Product permits termination notification within 15 days. Pharos applies termination on receipt/processing and retains the prior state until notified. terminationDate remains the actual employment termination date. iPass must preserve employee event order, including retries; automatic stale-event rejection is not implemented.

## Reserved environment field

ipass_role.env is nullable and reserved for future use. The current API does not accept, derive or default env. It is not an employee attribute or part of identity.
