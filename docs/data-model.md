# Pharos UAM data model

Pharos receives one employee and one account's complete approved role list per event.

## Tables and uniqueness

| Table | What it stores | Primary key | What prevents duplicates |
| --- | --- | --- | --- |
| employee | Current employee profile, manager and ACTIVE/TERMINATED status | employee_id from iPass | One row per employee_id |
| okta_account | Employee's Okta account for an application/environment | account_id: database-generated UUID | UNIQUE(application, environment, okta_account_id) |
| ipass_role | Shared iPass role details | role_id: database-generated UUID | UNIQUE(application, environment, entitlement_value) |
| ipass_role_owner | Current owners of a shared role | (role_id, owner_id) | Same owner cannot appear twice for the same role |
| account_role_assignment | Current and past account-role assignments | assignment_id: database-generated UUID | Only one open assignment per (account_id, role_id), where removed_at is null |
| ipass_event | Submitted JSON and latest processing result | event_id: UUID from iPass | One row per event_id; identical retries do not repeat changes |

The account and role tables also have scope uniqueness constraints used by foreign keys. These ensure an assignment's application/environment matches both its account and role.

## How they connect

~~~mermaid
erDiagram
    EMPLOYEE ||--o{ OKTA_ACCOUNT : has
    OKTA_ACCOUNT ||--o{ ACCOUNT_ROLE_ASSIGNMENT : receives
    IPASS_ROLE ||--o{ ACCOUNT_ROLE_ASSIGNMENT : assigned_as
    IPASS_ROLE ||--o{ IPASS_ROLE_OWNER : has_owners
    IPASS_EVENT ||--o{ ACCOUNT_ROLE_ASSIGNMENT : starts
    IPASS_EVENT o|--o{ ACCOUNT_ROLE_ASSIGNMENT : closes
~~~

Managers are stored directly in employee. Role owners do not need employee records. Event employee/account identifiers are not foreign keys because an event can arrive before those records exist.

## Internal IDs versus source IDs

| Internal Pharos reference | Source identifier from iPass |
| --- | --- |
| okta_account.account_id: UUID generated by PostgreSQL | okta_account.okta_account_id: Okta account identity |
| ipass_role.role_id: UUID generated by PostgreSQL | ipass_role.entitlement_value: source role identity |

Assignments and owners reference the internal UUIDs. Updating an existing account or role preserves its UUID.

## What happens when data changes?

| Change | Stored result |
| --- | --- |
| Add a role | Create an assignment; reuse the shared role if it exists |
| Remove a role | Close the assignment; keep history, role and owners |
| Assign a previously removed role again | Create a new assignment period |
| Send complete role list | Close omitted roles for that account only; [] closes all its assignments |
| Terminate employee | Mark TERMINATED and close assignments across all accounts in that deployment |
| Approved correction/rehire | Require USER_PROVISIONED; restore only roles supplied for that account |
| Retry same event UUID and payload | Return SUCCESS without repeating applied changes |
| Reuse UUID with changed payload | Reject with HTTP 409 |

Profile, role and owner data represent the latest state. Assignment history and submitted event payloads are retained. An existing account cannot be moved to another employee through this API.

## Timestamps and processing

| Field | Meaning |
| --- | --- |
| event_effective_at | When the change reported by iPass took effect |
| employee_last_synced_at | When iPass last refreshed employee details from Workday/VNDLY |
| received_at / processed_at | When Pharos first received the event / finished the latest processing attempt |
| assigned_at / removed_at | Source assignment start / when Pharos closed the assignment |
| created_at / updated_at | Pharos record creation / latest update |

removed_at does not confirm when iPass removed its membership. Termination must reach every relevant deployment immediately, independently of iPass's cleanup period.

Event status is RECEIVED, APPLIED or FAILED. Pharos populates error_code and error_message on failure and clears them on success. Business changes and APPLIED status commit together; failure rolls business changes back.

## Agreements with iPass

- Employee IDs must remain unique and stable across Workday/VNDLY and rehire.
- Events must arrive in order, including retriggers; no automatic stale-event rejection is implemented.
- Role and owner snapshots must contain current shared metadata.
