# Pharos UAM data model

One employee can have multiple Okta accounts. Each provisioning/update payload supplies the complete current Pharos role list for one `user.oktaAccountId`.

## Tables and uniqueness

| Table | Stores | Primary key | Duplicate prevention |
| --- | --- | --- | --- |
| employee | Current profile, manager, job details and supplier | employee_id | One row per employee identity |
| okta_account | An employee's Okta account | account_id, generated UUID | Unique okta_account_id |
| ipass_role | Shared source role definition and flags | role_id, generated UUID | Unique entitlement_value |
| okta_account_role_assignment | Current and historical assignment periods | assignment_id, generated UUID | One open assignment per account_id + role_id |
| ipass_event | Submitted payload and latest processing result | event_id, UUID from iPass | One row per event UUID |

There are five tables, 62 columns and five foreign keys. Internal UUIDs are generated by PostgreSQL. Source employee IDs, Okta account IDs and entitlement IDs remain strings.

## Relationships

~~~mermaid
erDiagram
    EMPLOYEE ||--o{ OKTA_ACCOUNT : has
    OKTA_ACCOUNT ||--o{ OKTA_ACCOUNT_ROLE_ASSIGNMENT : receives
    IPASS_ROLE ||--o{ OKTA_ACCOUNT_ROLE_ASSIGNMENT : assigned_as
    IPASS_EVENT ||--o{ OKTA_ACCOUNT_ROLE_ASSIGNMENT : creates
    IPASS_EVENT o|--o{ OKTA_ACCOUNT_ROLE_ASSIGNMENT : closes
~~~

Each assignment references one account, one role and its creation event. Its removal event stays null until closed. All five foreign keys use ON DELETE RESTRICT.

Manager IDs are source attributes; the manager does not need a Pharos employee record. Event employee/account identifiers are not foreign keys because receipt can precede profile creation.

## Payload mapping

| Payload | Stored in employee, unless stated otherwise |
| --- | --- |
| user.employeeId | employee_id; source Owner ID |
| user.sourceSystem | source_system: WORKDAY or VNDLY |
| user.employeeClass | employee_class; source classification such as Employee or Contractor |
| user.companyName | company_name |
| user.businessUnit / city | business_unit / city |
| user.manager | manager_employee_id, manager_first_name, manager_middle_name, manager_last_name |
| user.jobDetails | department, job_code, job_title, job_family_group, job_family |
| user.supplier | supplier; contractor supplier name |
| user.oktaAccountId | okta_account.okta_account_id |
| user.iPassRoles[].entitlementValue | ipass_role.entitlement_value |

ACTIVE snapshots require all profile fields shown in Swagger except email and supplier. Both may be omitted or null; either clears the saved value. Employee and manager middle names may be null. All five jobDetails keys are required, but their values may be null. ACTIVE requires terminationDate: null.

Names come from iPass as separate fields. Source Owner First/Last identify the employee; role ownership is not supplied. Environment is not supplied or inferred.

## Account isolation and history

| Employee ID | Okta account ID | Entitlement |
| --- | --- | --- |
| WU100482 | 00u8k3m5n7P2qRsTu0h7 | 00g8n4q2r6T9vWxYz0h7 |
| WU100482 | 00u9j4n6p8Q3rStUv0h7 | 00g9p5s3u7V2xYaBc0h7 |

These are two accounts for one employee. Updating one account's role list leaves the other unchanged. An account cannot move to another employee. Shared role metadata is stored once per entitlementValue.

Removing a role closes its assignment; it does not delete the role or history. An empty role list closes every assignment for the supplied account. Termination closes current assignments across all employee accounts immediately. Approved USER_PROVISIONED restores only the supplied account's roles and creates new assignment periods.

The internal employee GET returns current assignments by default. `includeHistory=true` also returns removed periods. An account with no current roles remains with `assignments: []`.

## Processing and timestamps

| Column | Meaning |
| --- | --- |
| employee_last_synced_at | When iPass refreshed employee details from Workday/VNDLY |
| event_effective_at | When the reported change took effect |
| received_at / processed_at | Pharos first receipt / latest processing completion |
| assigned_at / removed_at | Source assignment start / when Pharos closed the assignment |
| assignment_event_id / removal_event_id | Event that created / closed the assignment |
| created_at / updated_at | Pharos record timestamps |

removed_at does not confirm removal in iPass. Event processing status is RECEIVED, APPLIED or FAILED. Business changes and APPLIED status commit together; failures roll back business changes and record the failure where possible.

Identical applied retries do not repeat changes. Changed content under the same UUID is rejected with HTTP 400. iPass must preserve employee event order across accounts and retries; automatic stale-event rejection is not implemented.
