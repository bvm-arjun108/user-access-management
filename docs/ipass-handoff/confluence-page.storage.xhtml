Pharos UAM — iPass integration

iPass sends employee details and approved Pharos role assignments. Pharos stores the employee, each Okta account and its role history.

Request headersContent-Type: application/json; optional Accept: application/json
AuthenticationTo be agreed before shared deployment. The current implementation has no authentication.
TroubleshootingPharos returns X-Correlation-ID on every response. Save it with the event ID.

When to send an event

EventSend whenPayload / result
USER_PROVISIONEDFirst approved Pharos access, approved rehire or termination correction.Full ACTIVE profile, one account and at least one current approved role.
USER_UPDATEDRoles or employee details change; another account is added for an active employee.Full ACTIVE profile, one account and its complete current role list. An empty list removes all roles from that account.
USER_TERMINATEDEmployment termination becomes effective.Employee ID and TERMINATED status; termination date when known. Closes every current role assignment for that employee across all stored accounts.

Do not send hires without Pharos access, pending requests or unrelated application roles. Send termination immediately, including for previously provisioned employees with no remaining roles; do not wait for the 15-day iPass cleanup. USER_UPDATED cannot restore terminated employment.

Payload rules

RuleRequirement
Account scopeOne employee and one oktaAccountId per provisioning/update call. Send separate calls for distinct Okta accounts.
Complete role listuser.iPassRoles contains all current Pharos roles for that account. Omitted roles are removed. Missing/null is rejected. Maximum 500 roles.
IdentityEmployee: employeeId (source Owner ID). Account: application + oktaAccountId. Role: application + entitlementValue. Keep identifiers stable and preserve their case.
Environment / ownersNo environment field or inference. Source Owner First/Last describe the employee; role owners are not supplied.
Employee fieldsUse every field in the full example. email and supplier may be omitted or null; either clears its saved value in a full update. middleName may be null. ACTIVE requires terminationDate: null. Manager ID, first name and last name are required; manager middleName is required but may be null.
Role fieldsEvery shown role field is required. assignmentStatus is always PROVISIONED; isPharosGroup must be true. Send JSON booleans, not strings. Requestability/privilege flags are metadata.
DatesDates: YYYY-MM-DD. Timestamps: RFC 3339 with timezone. eventEffectiveAt is when the change took effect; employeeLastSyncedAt is when iPass refreshed employee details from Workday/VNDLY.
Assignment timeassignedAt is the original start of the current assignment. Preserve it while membership continues; it cannot follow eventEffectiveAt.
ValidationSend nonblank strings without surrounding whitespace. Do not send future-effective changes. Full field types and limits are in Swagger.

The jobDetails object contains department, jobCode, jobTitle, jobFamilyGroup and jobFamily. Include all five keys; use null for unavailable values. A null value clears the previously stored value.

supplier is the contractor supplier name from iPass. It is optional and may be null; missing/null clears the stored supplier in a full profile update.

Responses and delivery

HTTP 200 means the event was saved successfully or was already applied. An identical retry has no additional effect.

json
OutcomeiPass action
200Mark delivered.
400Resolve the invalid payload, identity conflict or business rule. Submit corrected content with a new event UUID.
Timeout / connection failure / 500Retry the same event UUID and unchanged payload with backoff. If retries fail, retain the event for investigation and replay.

Generate a new UUID for each new event. Reuse that UUID only for delivery of the identical event. Preserve event order per employee across all accounts, including retries. Pharos does not reject stale events automatically; do not replay an older snapshot after a newer one. Agree retry limits and urgent termination-failure escalation before go-live.

Error JSON contains timestamp, status, code, message and correlationId. Use the message to resolve the failure; provide eventId and correlationId to Pharos support.
